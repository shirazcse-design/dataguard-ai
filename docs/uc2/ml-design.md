# UC2 ML design: behavioural anomaly detection

> Unsupervised model training does not use anomaly labels; labels are used only for evaluation.

Configuration: `config/insider/insider.v1.yaml` (changing any value is a new `insider_version`).
Results: [`results/ml-eval.md`](results/ml-eval.md), generated by `dataguard-insider ml eval`
(offline, deterministic).

## 1. Synthetic data (`ml/insider/synth.py`, seed 20261003)

* **60 users, 7 role families:** engineering 14, finance 10, sales 10, research 8, product 8, IT
  operations 6, people operations 4. Name-free ids, no demographic, region or HR attributes.
* **90 days** from 2026-06-01. Days 1-60 are the historical period (normal behaviour only, used to
  train). Days 61-90 are the holdout: normal days, **54 hard-legitimate** user-days and **18
  injected anomalies**.
* **Anomalies (S1-S8):**
  * the flagship (u-2043, day 86) and its precursor;
  * a slow drip over 10 days;
  * a source-code grab;
  * repository exploration with access failures;
  * credential probing;
  * an after-hours bulk download and upload;
  * a subtle single new repository with a small upload;
  * an upload spike with sensitive customer data.
* **Hard-legitimate (H1-H5):** month-end close (finance), release week (engineering), an approved
  migration, after-hours work while travelling, and new-project onboarding. These exist to make
  false positives visible.

## 2. Features (`ml/insider/features.py`)

Seven raw daily features: files downloaded, sensitive files accessed, after-hours activity,
external upload volume (MB), new repository access, failed access attempts, and distinct
repositories. The first six are the PRD's; distinct repositories is a justified addition.

Each becomes a **robust z-score against that user's own baseline for the same day type** (weekday
vs weekend):

  z = (x − median) / max(1.4826 · MAD, floor)

The per-feature **floor** stops a zero-variance history from turning one small event into an
extreme value. For example, a user who never uploads would otherwise get an infinite z on a 1 MB
upload. A `log_download_ratio` input adds a scale-aware view of downloads.

Holdout days are scored against a **frozen baseline** (the last 28 training days), so an anomaly
can't hide by contaminating its own baseline.

## 3. Models (`ml/insider/detectors.py`)

| | Isolation Forest (authoritative) | Statistical baseline (comparison) |
|---|---|---|
| Inputs | the 7 robust z-scores + log download ratio | the same z-scores |
| Training | 200 trees, `max_samples` 256, seed 20261003, scikit-learn 1.9.1; normal training days only | none (a rule) |
| Output | score in [0, 1]; bands from **training** percentiles: ELEVATED ≥ p95 (0.5273), HIGH_ANOMALY ≥ p99 (0.6025) | flag if any z > 3, or ≥ 2 features with z > 2 |
| Explanation | reset-to-baseline counterfactual per feature ("score falls by X if downloads were normal") | which z-scores crossed the rule |

The contributions explain the score; they are not evidence of intent. Thresholds come from score
percentiles, so no label touches the model or its bands.

## 4. Evaluation (holdout, labels used only here)

| | Isolation Forest | Statistical baseline |
|---|---|---|
| ROC-AUC | **0.9942** | 0.9937 |
| Precision / recall at 1 alert/day | **0.467 / 0.778** | 0.400 / 0.667 |
| Precision / recall at 3 alerts/day | 0.200 / **1.000** | 0.189 / 0.944 |
| Release-week user-days alerted (3/day) | **7** | 15 |
| Subtle anomaly (S7) caught | **yes** | no |

**Reading:** ROC-AUC barely separates them, but at a realistic analyst budget the Isolation Forest
is more precise. It catches the subtle case, and it alerts on half as many release-week days. That
is the product argument for per-user, multivariate scoring over a threshold rule.

**Fairness by role family (normal days, not tuned):** IF alert rates range from **1.3% (product)**
to **8.9% (IT operations)**:

| Role family | Alert rate |
|---|---|
| Product | 1.3% |
| Finance | 1.5% |
| People operations | 2.5% |
| Research | 3.8% |
| Sales | 5.4% |
| Engineering | 5.9% |
| IT operations | 8.9% |

High-variance roles alert more. The rate is reported per family so an operator can set per-family
budgets. It isn't hidden by re-tuning. Role family is the only grouping measured: the data holds no
protected attribute, by design.

## 5. Limitations

* Synthetic behaviour from one generator: the separation is optimistic, and the scenarios are known
  to their author.
* 18 anomalies is a small positive set; one run, no confidence intervals.
* Day-type baselines don't model holidays, role changes or seasonality beyond weekday/weekend.
* No drift monitoring or retraining policy (retraining would be a gated change, see
  [`learning-loop.md`](learning-loop.md)).
